Virtual Families 2 Restoration/Addition Patcher Transparency Log
================================================================

Purpose
-------
This document began with the offline VF2 patcher design used by the B105
refresh and is maintained through B150. Each exported patcher bundle also
generates its own Transparency Log.txt with exact manifest counts, paths,
feature gates, and changelog details for that bundle.

Creation disclosure
-------------------
This offline patcher was created with Codex AI in collaboration with Lorsieab2.
The display name is Virtual Families 2 Restoration/Addition Patcher. The
GUI starts from Launch_GUI.bat. Prebuilt Launch GUI.lnk shortcuts are not
shipped because Windows shortcut targets are path-specific and can break after
ZIP extraction. No compiled patcher launcher EXE is shipped in patcher bundles.
The update/release repository is Virtual Families 2 Restoration/Addition
Patcher, published as the private GitHub repo
https://github.com/Lorsieab2/Virtual-Families-2-Restoration-Addition-Patcher/releases.
New patcher releases should be uploaded there only.

What the patcher does
---------------------
- Verifies the user-selected vanilla Virtual Families 2 executable before
  applying patches.
- Verifies the selected folder has the official LDW website install shape
  before creating a modded output folder, backup, or changed file.
- Reads patch records and asset records from manifest.json.
- Applies only records whose required settings are enabled.
- Creates backups before writing changed files.
- Writes machine-readable success/failure logs.
- Streams per-record validation/apply progress to the CLI and GUI.
- Creates a separate, clearly labeled modded output folder by default.
- Refreshes recognized VF2-*-Modded output folders from vanilla before applying
  currently checked records, so unchecking a patch and clicking
  Enable/Disable Patches removes the prior optional change.
- Names the modded executable clearly so it is not confused with vanilla.
- Supports Dry Run / Validate Only, which validates that the patcher's working
  and does not actually change or write files.
- Provides restore support for backups created by the patcher.

What the patcher does not do
----------------------------
- Does not inject code into a running game.
- Does not edit process memory.
- Does not use obfuscation or packers.
- Does not require admin-only install locations.
- Does not alter original saves unless the user manually copies saves.

Official install validation
---------------------------
The patcher refuses to apply patches unless the selected vanilla folder has
these exact top-level entries:
- Assets
- fmod.dll
- icon.bmp
- Images
- ldw.ini
- libjpeg-9.dll
- libpng16-16.dll
- Readme.txt
- SDL2.dll
- SDL2_image.dll
- Sounds
- uninst.exe
- Virtual Families 2.exe
- Virtual Families 2.url
- zlib1.dll

If validation fails, the user-facing popup says:

No valid Virtual Families 2 Installation detected! Are you sure you downloaded it from the official website?

Links:
http://www.ldw.com/
http://www.virtualfamilies.com/index.php

Dry Run / Validate Only
-----------------------
ELI5: Dry Run validates that the patcher's working. It checks that the selected
Virtual Families 2 folder looks official, checks that the EXE is the expected
one, checks that the patch instructions and payload files match their hashes,
then stops. It does not actually change or write files. Use it when you want to
ask, "Would this patch work?" before actually applying it. If no custom log
path is selected, dry-run and pre-write failure logs are written beside
manifest.json so the vanilla game folder stays untouched.

Payload folder
--------------
The payload/ folder is the patch bundle's local stash of files that may be
copied into the separate modded output folder. It is not applied blindly. Each
file must be referenced by an asset_patches record in manifest.json, and the
patcher verifies the payload file's source_sha256 before copying it.
During apply, payload/ is read-only/copy-only. The patcher reads payload
sources and copies enabled records into the generated modded output folder; it
does not write back into payload/.

Payload contents are intentionally lean:
- payload/Assets/: changed .fmap files and other required runtime asset
  metadata.
- payload/Images/: changed generated sprites, runtime images, Outfit icons,
  villager sheets, TV animation strips, furniture art, and UI art.
- payload/OptionalVisualMods/: source-only optional visual-mod files such as
  custom
  map images, transparent UI bars/tabs, and Invisible Furniture visible or
  transparent graphics.
- payload/Original Virtual Families 2 Assets/: source-only preserved vanilla
  reference/assets used for transparency and restore metadata.
- payload/OptionalSongMods/: source-only optional VF1/VF2 song .ogg files.

Unchecked patch settings should leave their payload files unused and, for
feature-specific payloads, absent from a refreshed modded output folder.
Optional visual source folders, OptionalSongMods, and Invisible Furniture
visible/transparent graphics are assigned to their own default-off settings so
unchecking those settings omits their records on the next Enable/Disable
Patches run.

Optional visual output rules:
- Furniture graphics write to Images/Furniture.
- Future Workshop, Kitchen, and Office upgrade graphics write to
  Images/Upgrades.
- Animation strips, UI graphics, and other loose images write to Images.

Optional song output rules:
- Enabled OptionalSongMods records copy payload/OptionalSongMods/*.ogg to
  Sounds/*.ogg.
- Disabling OptionalSongMods and clicking Enable/Disable Patches refreshes the
  modded output from vanilla so the original Sounds/*.ogg files return.

Custom Couches and LDW Posters/Paintings now have a separate default-off
setting. Asset payload routing covers the Colorful Couches, LDW Modern
Paintings, and LDW Poster/Painting files. Current native store-row support for
those items still comes from the full modded EXE payload until those native
table edits are split into individual setting-gated patch records.

Important files
---------------
- work/offline_vf2_patcher.py: CLI patcher, manifest validation, backups,
  restore, per-record progress, and JSON patch logs.
- work/offline_vf2_patcher_gui.py: Tkinter GUI for choosing the vanilla game,
  toggling settings, applying patches, restoring backups, and showing the
  completion summary.
- work/export_offline_patch_bundle.py: source-side exporter that creates
  manifest.json, payload files, runner scripts, and generated Transparency
  Log.txt.
- How to Use.txt: player-facing instructions bundled with exported patcher ZIPs.
- work/patch_mobile_furniture_pack.py: current build generator that produces
  the modded beta folder used as patcher payload input while native byte/table
  records are still being extracted.

Historical B105 behavior
------------------------
- The manifest declares a separate output folder named VF2-B105-Modded for the
  B105 patcher bundle.
- The B105 patcher bundle does not ship a compiled patcher launcher EXE.
  Launch_GUI.bat starts the GUI. Launch GUI.lnk is intentionally omitted.
- The B105 patcher bundle should use native byte/table patch records for
  code/table changes, then write the result as a clearly renamed modded EXE so
  the modded folder does not leave an ambiguous Virtual Families 2.exe beside
  it.
- Optional visual settings default off.
- OptionalSongMods defaults off and targets Sounds/*.ogg when enabled.
- Add unused pets defaults on for the Turtle/Hamster pet-store metadata.
- Invisible Furniture visible graphics and transparent graphics are separate
  default-off settings.
- Add Custom Couches and LDW Posters is a separate default-off setting.
- Settings Evict and Island Events are default-off Optional patches. Mobile
  furniture behaviors and Holiday Ornaments remain default-off Experimental/Not
  Working patches.
- Patch settings are grouped in the GUI as Main Patches (green), Optional
  Patches (black), and Experimental/Not Working Patches (red).
- patcher_icon.png is shown beside the bold GUI title, and patcher_icon.ico is
  used by the GUI window/shortcut icon when available.
- The GUI completion popup lists enabled patches, disabled/restored patches,
  altered files, the modded game folder, and the modded save folder.
- Launch_GUI.bat passes adjacent manifest.json to the GUI, but the GUI does not
  open the vanilla-folder picker automatically. The user selects their own
  vanilla Virtual Families 2 installation folder manually. It does not look for
  or assume a hardcoded install path.
- Modded saves are expected under Documents/LDW/(name of modded Virtual
  Families 2 exe).
- Existing vanilla saves can be copied manually into the modded save folder.
  Original saves remain untouched.

Unchecking patches
------------------
Unchecked asset and file settings are reverted by omission when the patcher
refreshes a recognized VF2-*-Modded output folder from vanilla. Their records
are not copied, replaced, or created on the next Enable/Disable Patches run.
This applies to OptionalSongMods, optional visual source folders, active
transparent UI swaps, custom map images, Invisible Furniture visible graphics,
and transparent Invisible Furniture swaps.

Historical B105 limitation
--------------------------
The B105 release direction is to avoid distributing a prebuilt modified game
EXE. Native/code/table changes should be represented as explicit byte/table
patch records where possible, applied locally after validating the user's
vanilla EXE. Full modded EXE payloads remain a diagnostic fallback only when a
change cannot yet be represented safely as records.

B150 post-release hotfix transparency
--------------------------------------

- A user runtime test proved that enabling Holiday Ornaments in the first B150
  archive caused an access violation shortly after the house appeared and when
  opening the Collections Chest. The source overlay and release asset were
  treated as faulty even though Main + Optional without Holiday worked.
- The cause was unsafe insertion into native x86 function bodies. COFF symbols
  and relocations moved, but internal relative branches did not. The replacement
  uses fixed-size detours and appended code caves for HandleMouse, Find, and
  WasItemSpawned; repairs The Collector Keep branch; stops the incomplete Drop
  reentry loop; uses correct imm32 comparisons for 0x9E; and makes
  Ornamentologist/Goal Collector completion idempotent.
- The remaining praise-string bug was also reproduced in native control flow:
  normal praise called ForgetPlans, which erased the current 0x28-byte action
  string before the behavior variation wrapper ran. Behavior Patches now
  captures and restores those exact bytes around the normal InvokeReward path.
  The deliberate over-praise RunAway path is unchanged.
- Cheat Upgrade 0x12D, Fix all house malfunctions, clears all 11 malfunction
  props and returns Router prop 0x17 online without touching ant puzzle props.
  Trigger All sets Router Offline. Cheat rows are displayed in functional
  groups without renumbering any existing IDs.
- Dryer lint fire was verified as a legitimate stock random malfunction, not
  merely a cheat effect. It requires Dryer object 0x48, sets prop 0x21, and its
  native repair clears the prop and advances Handyman achievement 0x3A. The
  build validator now fails if that selector/gate/repair contract drifts.
- Holiday Ornaments remains default-off Experimental until the replacement
  archive is manually retested in game. Automated branch and build checks do
  not substitute for that runtime test.
- GitHub's current immutable-release endpoint reports release immutability is
  disabled for the public patcher repository, allowing the faulty B150 asset to
  be replaced in place.
- New resource, pet, longevity, family-tree appearance, and Older Villagers
  requests are assigned to B151 and recorded in docs/B151-design.md. They are
  not silently included in this B150 hotfix.

B180 picnic and patio props not shipped
- The owner asked that the Picnic Table and Patio Table carry their meal and
  drink props. They are NOT shipped, and this is a hard engine limit rather than
  an oversight. CEnvironment::SetProp opens with `cmp edi, 54h` / `ja`, so the
  desktop build accepts prop ids 0x00 through 0x54 only. ePropPicnicReady is
  0x55 and ePropPatioDrinks is 0x56, both out of range. The fall-through path
  writes through [ecx + prop*16 + 0x7C], so passing either would corrupt memory
  rather than fail cleanly. The existing external-state approach was avoiding a
  crash.
- The bound was examined again for B180 to see whether it could simply be
  raised. It cannot, and the reason is worth recording so the question is not
  reopened as a one-byte change. The compare at Environment.obj+0xAB33 is
  `83 FF 54`, and raising it to 0x56 is indeed a single byte. But the three
  instructions that follow are `0F 87` (ja, past the end), `0F B6 87 <reloc>`
  (movzx eax, byte ptr [edi + index table]) and `FF 24 85 <reloc>` (jmp dword
  ptr [eax*4 + jump table]). This is a compiler-generated jump table, and both
  displacements are relocations resolved at link time. Admitting 0x55 and 0x56
  would read two entries past the end of the byte index table and jump through
  whatever followed. Doing it properly means extending both tables and writing
  case bodies for two props that have no desktop art and no desktop handler --
  a feature, not a bound adjustment.

B180 patcher GUI "Please wait" window
- The patcher copies whole game folders and renders patched bytes on the Tk
  main thread, so the main window stops repainting and Windows relabels it
  "(Not Responding)". Nothing is wrong when that happens, but it reads as a
  crash and players close the patcher mid-copy. B180 adopts the Virtual
  Villagers Fun Patcher's wait window, which gives that pause a face: a modal
  window reading "Please wait... / Loading the patches." over an indeterminate
  progress bar, with the work moved onto a worker thread so the event loop
  keeps painting.
- The close button on that window is deliberately inert. The work cannot be
  cancelled partway without leaving a half-copied game folder behind.
- Two defects were found in the port during review and fixed here, and both are
  worth recording because the second is a live bug in the patcher it came from
  and has been reported back to that project:
  - The modal grab was taken inside a bare try/except that swallowed TclError.
    Tk refuses the grab until the window manager has made the window viewable,
    so a failure left every control underneath live: the window still looked
    modal while a double-click on Apply could start two patch workers against
    the same output folder. It now retries against a two-second deadline and
    raises if the grab never lands. The obvious repair, wait_visibility(), is
    NOT used: it blocks forever when the window never becomes viewable, which
    is exactly what a withdrawn parent produces, and it hung the GUI suite.
  - Centring clamped the computed position to zero. On a multi-monitor desktop
    a window on a screen left of or above the primary display has legitimately
    negative root coordinates, so clamping threw the wait window onto the
    primary monitor - the worst case for a window holding a modal grab, since
    the application then appears locked while the thing explaining why sits on
    a screen the player may not be looking at. Only the screen-centred fallback
    is clamped now.

- The exporter collapses byte-identical payload files and points several
  manifest records at one canonical copy. This is long-standing behaviour, not
  new in B180: the B176 manifest already has five source files each serving two

  only acceptable when it can be shown to catch more, not less.

  source-tree tests answer whether the correct map is SELECTED; the extracted-
  payload check answers whether the correct map ARRIVES. Neither substitutes
  for the other, and the second is the one that speaks for what a player gets.

B180 the prop bound is TWO limits, not one, and they agree
- The picnic/patio props were previously documented as blocked by a single
  compare, CEnvironment::SetProp's `cmp edi,54h`. Re-examined after the owner
  supplied the artwork. There is a SECOND bound, and finding it changes what
  raising the limit would cost.
- CEnvironment::Update at Environment.obj+0xce4f ends its loop with
  `inc edi` / `cmp edi,55h` / `jl`, so it walks prop indices 0x00-0x54.
  SetProp at +0xab33 uses `cmp edi,54h` / `ja`, admitting 0x00-0x54. The two
  agree on exactly 85 props.
- The 0x55 in Update is the loop's terminator, NOT a spare slot. It would be
  easy to read it as one free index beyond SetProp's limit and conclude there
  was headroom for ePropPicnicReady (0x55); there is not, and both props
  remain past the end of the array.
- So raising the bound means changing at least three things in a stock object
  file that agree with each other today: SetProp's compare, Update's loop
  terminator, and the jump table SetProp dispatches through, whose index and
  target displacements are both link-time relocations. Any one of them left
  behind desynchronises the array from the code that walks it.
- This is why the shipped approach intercepts instead. VF2PatioSetPropAndTrack
  catches 0x55 and 0x56 before SetProp sees them and tracks the state
  externally, so the out-of-range ids never reach the engine. That is also why
  nothing crashes today and why nothing draws.
- Environment.obj carries a table-driven prop system -- PropTypeStruct,
  InitProps, RefreshProps, UpdateProps, GetPropPosition, SetPropPosition,
  PropIsActive -- with no static prop table in .data, so the array is built at
  runtime by InitProps. There are no prop art filenames in the object either,
  so art is resolved elsewhere.

B180 how the picnic and patio props would actually be drawn
- Traced after the owner supplied the artwork. Recorded because it changes the
  route from "extend a jump table in a stock object" to "wrap one function",
  and because the shape of the call sites decides how the wrapper must work.
- Props are not blitted directly. Environment.obj calls CDecal::RefreshDecals,
  and CDecal::RefreshProps is what draws them. It calls BOTH AddDecal
  overloads: 19 calls to (ldwImageGrid *, int, int, float) and 25 to
  (ldwImageGrid *, int, int, int, float), counted from the relocations
  inside RefreshProps rather than estimated. An earlier draft of this entry
  said 'sixteen times, once per prop type'; that was wrong on both the
  count and the one-per-type reading, and review caught it. AddDecal is
  public and takes an image grid plus world coordinates, so it can draw a
  sprite the prop enum never has to know about.
- That is why the SetProp bound is not the real obstacle to RENDERING. The
  bound stops an id being stored in the prop array; it does not stop anything
  being drawn. A wrapper around CDecal::RefreshProps can draw the meal and
  drinks sprites from the state VF2PatioSetPropAndTrack already tracks --
  gVF2PicnicReadyOn, gVF2PatioDrinksOn and their deadlines -- without the ids
  ever entering the array.
- Six call sites reach RefreshDecals from Environment.obj: ClearProp +0x104,
  Refresh +0x18, RefreshProps +0xe6, SetProp +0x33b, SetPropGroceries +0x98
  and UpdateProps +0x53. CDecal::RefreshDecals reaches CDecal::RefreshProps
  from exactly one site, +0xb70.
- IMPORTANT for the wrapper: that site and CEnvironment::RefreshProps +0xe6 are
  `jmp rel32` TAIL CALLS (opcode 0xE9), not `call rel32`. Retargeting a tail
  call REPLACES the callee rather than wrapping it, so the helper must invoke
  the original itself and must not expect to return into the caller. A
  wrapper written for a `call` site would silently drop the stock prop
  drawing, which is far worse than the missing props it set out to add.
- No change to Environment.obj is needed for any of this, which is why it is
  the safe route: it is the relocation-retarget pattern already proven by
  VF2PatioSetPropAndTrack.
- The two inputs a wrapper still needs, traced but not yet built:
  IMAGE. AddDecal takes an ldwImageGrid *, obtained from
  theGraphicsManager::GetImageGrid(EImage), which the generator already
  calls. New ids are allocated past ORIG_IMAGE_MAX (0x27C) by the existing
  image_id_for / lock_image_id_for / visible_special_upgrade_icon_id_for
  scheme, and a new image is registered by cloning a donor's 0x30-byte
  descriptor and rewriting its grid dimensions from the PNG's real size.
  So registering the three prop sprites uses machinery that already ships.
  POSITION. RESOLVED, but NOT as 'use two literals' -- see the decal-call
  entry below and read its correction before implementing. What is resolved
  is how the engine takes a position: 43 of 44 stock calls pass immediates
  and one computes it, so both forms work and GetPropPosition is not
  required. What is NOT resolved is which position these two props should
  use, and literals are the wrong answer for them: a table can be moved and
  a player can own more than one, so the sprite has to follow the specific
  table the villager used. That means retaining the furniture slot that
  VF2PatioSetPropAndTrack currently discards.

B180 what a prop decal call actually looks like
- Decoded from CDecal::RefreshProps rather than inferred, because the wrapper's
  arguments depend on it and guessing them would draw in the wrong place.
- The first call in that function reads, in full:

    8b c3                    mov  eax, ebx              ; ebx = prop index
    c1 e0 04                 shl  eax, 4                ; index * 16
    80 b8 7c 00 00 00 00     cmp  byte [eax+0x7c], 0    ; the active flag
    0f 84 ...                je   skip                  ; inactive: draw nothing
    51                       push ecx
    c7 04 24 00 00 80 3f     mov  dword [esp], 1.0f
    8b cf                    mov  ecx, edi              ; this = CDecal *
    68 ff 00 00 00           push 0xff
    68 46 01 00 00           push 0x146
    ff b7 2c 18 00 00        push dword [edi+0x182c]    ; ldwImageGrid *
    e8 <reloc>               call AddDecal

- Two things follow, and both matter for the wrapper.
- FIRST, the prop record stride is confirmed as prop*16 + 0x7C, matching what
  the request ledger recorded from the SetProp fall-through. The shl eax,4 is
  the *16 and 0x7c is the active-flag field. There are 43 such flag reads in
  RefreshProps, all of the form [eax+0x7c] with eax recomputed per prop, so the
  index lives in ebx rather than in the displacement.
- SECOND, and this settles a question previously recorded as unconfirmed:
  the decal coordinates are IMMEDIATE CONSTANTS in 43 of the 44 calls. The
  first passes x=0x146 and y=0xff as literals, not values read from a
  furniture record, so those props' positions are baked at compile time.
  The single exception is the four-argument call at RefreshProps+0x6e5,
  which pushes esi and dword [eax] -- a computed position. It is recorded
  because an earlier draft of this entry said ALL the coordinates were
  immediates, which was an overstatement caught in self-review, and
  because it proves the engine supports both forms. A wrapper may use
  literals, as the majority do, without that being the only option.
- AND FOR THESE TWO PROPS IT MUST NOT. Review corrected the conclusion
  drawn above, and the correction is the important part. Stock props are
  fixtures at one place in the house, so a baked literal is right for
  them. A picnic or patio table is FURNITURE: the player can move it, and
  can own more than one. Two fixed literals would draw the meal at one
  spot regardless of which table the villager actually used, and would
  keep drawing it there after the table was moved.
- That is a design flaw in the wrapper as sketched, not a detail. The
  existing behaviour code already resolves a specific instance --
  LinkPeepToFurniture and VF2FurnitureSlotAtPoint both work per slot --
  but VF2PatioSetPropAndTrack keeps only global on/deadline state
  (gVF2PicnicReadyOn, gVF2PatioDrinksOn, gVF2PicnicPreparer) with no slot
  index. So the state that would be needed to place the sprite is
  discarded at the moment it is known.
- The remaining work is therefore larger than 'pick two literals': the
  tracking has to retain WHICH table, and the wrapper has to read that
  table's position rather than a constant. The exception at +0x6e5 shows
  the engine accepts a computed position, so the route exists; what it
  needs is the slot kept rather than dropped.
- SUPERSEDED: an earlier draft of this entry concluded from the immediates
  that a wrapper 'does not need to resolve a furniture record's world
  position at all' and needs only two constants per sprite. That is wrong
  for these two props, for the reason given directly above, and it is left
  here marked rather than deleted because it is the tempting conclusion and
  someone will reach it again. A wrapper for the picnic and patio props DOES
  need the selected table's position.
- The active-flag check also means a wrapper cannot simply always draw. Stock
  props draw only when their flag is set; the two added props have no flag in
  the array, which is exactly why VF2PatioSetPropAndTrack keeps their state
  externally. The wrapper's condition is that external state, not [eax+0x7c].

B180 the recurring defect: what a check READS versus what it ASSERTS
- Nine separate defects this release were one fault wearing different clothes.
  Naming it here because it kept being rediscovered, each time as if new, and
  because the instances are only obvious together.
- The fault: a check's assertion and the thing it reads drift apart, and
  nothing fails, because what it reads still exists. A green result then means
  "the thing I looked at is still there", not "the claim is still true".
- The nine, with what each actually read:
  1. README settings count       read the exporter, claimed the bundle
  2. disclosure guard            inside a bundle-gated class; skipped on every
                                 clean checkout and guarded nothing
  3. digest requirement          searched the whole log, claimed the correction
  4. prop honesty warning        landed in the repo README; a player reads the
                                 GUI's manifest description
  5. keyword guard               searched for the right topic's words in the
                                 wrong paragraph
  6. symbol-class filter         collected EXTERNAL only; STATIC boundaries
                                 were invisible, so a slice ran past them
  7. relocation check            verified the target, discarded the type;
                                 DIR32 and REL32 both link and differ
  8. AddDecal overload           accepted either, when the pushed bytes admit
                                 exactly one
  9. archive selection           sorted by filename and answered from B178
                                 while B180 was the release
- Two of these were found by writing a check and having it pass when it should
  not have. Seven were found by review. That ratio is the argument for review
  rather than for more checks.
- What actually catches it, in the order that has worked here:
  FORGE A KNOWN-BAD INPUT. Every object-level check in this area is validated
  against a deliberately broken copy -- a flipped opcode, a retargeted
  relocation, a rewritten coordinate -- and the object restored byte-identical
  afterwards. A check never shown to fail has not been tested, only run.
  PIN EXACT NUMBERS, NOT THRESHOLDS. "19 and 25" caught a filter that silently
  matched nothing; "greater than zero" would have passed on an empty list.
  ASK WHAT THE CLAIM IS ABOUT. A statement about a bundle cannot be checked
  against the source that generates it. A statement about what a player sees
  cannot be checked against a file they never open.
  MAKE GUARDS EXPIRE. A guard that cannot stop applying becomes an obstacle to
  the change it exists to shepherd, and the pressure is then to delete it.
- The counter-case is worth keeping too: the holiday ornaments description
  says twelve collectibles and ships twelve. It was checked the same way and
  was correct, and is now pinned so a later pass does not "fix" a right
  number.

    per-prop record: CEnvironment + prop*16
      +0x7C  active byte
      +0x84  X
      +0x88  Y

- This confirms the ledger's [ecx + prop*16 + 0x7C] note from a second,
  independent function, and identifies 0x7C as the active flag -- the same
  byte the draw path tests with `cmp byte [eax+0x7C], 0`.
- The consequence decides the design. Prop 0x54 is the last stock record and
  ends at +0x5CC; 0x55 and 0x56 would need 32 bytes beyond it. So calling
  SetPropPosition for either id writes past the array end -- the same
  out-of-bounds write SetProp's bound prevents, reached through a different
  function. A wrapper must therefore keep its own position beside the flags it
  already keeps, and pass those coordinates to AddDecal directly. That
  GetPropPosition cannot answer for these ids is correct behaviour, not an
  obstacle to route around.
- The decal side, from Decal.obj: AddDecal is a slot insertion into a 256-entry
  array of 24-byte slots, found by scanning for a zero first byte. Neither
  overload has relocations, so a wrapper can call one directly.
- The two overloads are NOT equally safe, which matters more than their arity.
  The five-argument form (grid,int,int,int,float) bounds-checks with
  `cmp edx,0x100 / jg`. The four-argument form (grid,int,int,float) has no
  comparison against any bound anywhere in its 69 bytes -- checked for every
  register form. Adding draws through the unguarded one when the array is near
  full would write past slot 256.
- Neither RefreshDecals nor RefreshProps pushes 0x55 or 0x56, so there is no
  existing draw site to substitute at. The wrapper adds draws that were never
  there, rather than replacing an existing push the way the bathroom curtain
  patch does.

The furniture-array sanity bound was twice the real capacity
- VF2FindFreeSpaLoungerSlot reads the placed-furniture record count out of the
  furniture manager and walks that many records. Before walking it rejects an
  implausible count, and that guard was written as 0x400.
- The engine's real capacity is 0x200. Both sites in FurnitureManager.obj that
  compare the count against an immediate do "cmp dword ptr [reg + 0x1004],
  0x200" followed by "jge <return without adding>", so the array refuses to
  grow past 512 records and a count above that cannot occur. A guard set at
  twice the capacity still admitted 512 records' worth of addresses the engine
  would never populate.
- Not exploitable on its own, because the walk is bounded by the same count it
  reads and the engine never writes a larger one. It was simply wrong against
  the binary, and a sanity guard that admits values the engine cannot produce
  is not doing the job it exists for.
- Found by the other session while self-reviewing the equivalent bound in its
  own change, and reported rather than edited, because this function is in a
  different lane. Verified here against the object rather than taken on
  report: scanning every comparison against the count field finds 28 sites, of
  which exactly two use an immediate, and both say 0x200.
- The test derives the constant FROM the object instead of restating it, so
  the source and the binary cannot drift apart silently, and it refuses if the
  two sites ever disagree rather than picking the first. It walks decoded
  instructions rather than reading a fixed displacement, because the cmp and
  its jge are not adjacent -- 0x0006 then 0x0010 in both functions -- which is
  the same trap that produced a garbage read in an earlier checker.
- Validated against known-bad: with the guard back at 0x400 the test fails and
  names both numbers; with the fix it passes.

B182 the picnic and patio props: four defects, all confirmed, all fixed
- The owner reported directly that "the props also don't draw on the picnic
  tables or the patios". They did not draw in B181 or in any earlier build.
  Four separate defects were responsible. Each was confirmed against the
  shipped B181 executable or against the engine's own disassembly, not from
  reading the diff, and the first of them made the other three invisible.

- 1. THE IMAGE DESCRIPTORS WERE RESERVED AND NEVER POPULATED.
  patch_graphics_manager() reserved three descriptor records for the sprites --
  the "+ len(PROP_ART_IMAGE_ORDER)" term in append_count -- but no loop ever
  wrote them. Every other image block sets an id, a path-symbol relocation and
  the grid dimensions; the prop block got zero-filled space and nothing else.
  The ids prop_art_image_id() computes therefore pointed at blank descriptors
  and GetImageGrid() could not resolve any of the three.
  The artifact says so exactly. Every populated descriptor carries a
  path-symbol relocation, so its path string ends up in the linked executable.
  In the shipped B181 binary:
      SpaLoungerStd.png   present     <- a populated descriptor
      mealSE.png          ABSENT
      mealSW.png          ABSENT
      patioDrinks.png     ABSENT
  in every form, with and without an "Images/" prefix.

- 2. THE DRAW WAS ON A CONDITIONAL PATH. All 48 AddDecal calls in
  CDecal::RefreshProps sit inside per-prop active branches of its switch. The
  wrapped site at +0xA6A is reached only by a jmp to 0xa62 from those branches
  and sits within two nested loops (cmp esi,4 and cmp ebx,0x55), so the props
  drew only while some unrelated stock prop happened to be active.
  There is no unconditional call site inside RefreshProps to move to, and every
  call in it is inside that switch.
  AN INTERMEDIATE ATTEMPT WRAPPED CDecal::InitDecals, RefreshDecals' first
  instruction. That is unconditional, which was the requirement, and it was
  WRONG -- InitDecals EMPTIES the decal array, so the capacity check in defect
  4 below would have run against freshly cleared storage, always found room,
  and the two added decals would then have pushed the STOCK pass past the
  256-slot end. A guard that reads as protection while causing the overflow it
  exists to prevent. It was caught in review before shipping.
  THE INSTALLED HOOK is CDecal::RefreshDecals' TAIL JUMP to
  CDecal::RefreshProps -- an E9 at +0xB6F whose REL32 relocation is at +0xB70,
  four bytes before the section end, and the ONLY REL32 reference to
  RefreshProps in the whole object. The wrapper,
  VF2RefreshPropsAndTableProps, calls RefreshProps and THEN draws, so the site
  is unconditional AND at final decal occupancy, which are the two constraints
  that have to hold at once.
  Still zero added bytes, because that jump is already five bytes with a
  relocation. The installer asserts exactly one such site and that it ends at
  the section end, so if RefreshDecals ever stops ending in a tail call the
  build fails rather than hooking it blind -- the wrapper CALLs RefreshProps
  and therefore needs a real return.

- 3. THE POSITION WAS THE WALK-TO ANCHOR, NOT THE TABLE.
  CFurnitureManager::FindFurniture ends by copying the matched record into
  sFurnitureInfo2 and adjusts the position on the way:
      +0x110  sub  esi, [eax]        ; hotspot x
      +0x115  sub  edx, [eax + 4]    ; hotspot y
      +0x121  mov  ecx, [ebx + 0x14] ; record x
      +0x124  mov  eax, [ebx + 0x18] ; record y
      +0x127  add  ecx, esi
      +0x129  add  eax, edx
      +0x137  mov  [edx + 8], ecx    ; -> info.point.x
      +0x12E  mov  [edx + 0xc], eax  ; -> info.point.y
      +0x13D  mov  [edx], eax        ; -> info.unknown0, the placement handle
  So info.point is the tile a villager stands on to USE the item. Drawing there
  puts the prop beside the table by however much that furniture map's hotspot
  is offset. The capture now finds the record by its unique placement handle
  and reads the record's own +0x14/+0x18 position and +0x10 orientation. An
  unresolvable handle suppresses the draw rather than placing a prop somewhere
  arbitrary.

- 4. THE DRAW COULD WRITE PAST THE DECAL ARRAY. Both AddDecal overloads walk
  the same free-slot scan -- occupancy byte at record + 0, stride 0x18 -- but
  only the five-argument form guards with cmp edx,0x100 / jg before writing.
  The four-argument form this feature calls has no comparison against any
  bound. The previous justification, that the callers are gated on a prop being
  placed so "at most two extra decals are ever added", bounds what the feature
  ADDS and not what is already there: with all 256 slots occupied by the stock
  refresh, the FIRST of these calls walks off the end.
  Switching to the guarded overload is not available. Its extra argument is a
  per-decal value RefreshProps reads from its own object -- [edi+0x1940]
  indexed by the current prop, at +0x25BB8 -- and no constant is correct in its
  place. The same bound is applied before the call instead, with the same
  stride and occupancy byte taken from the disassembly.

- WHY NOT THE PROP ARRAY AT ALL: CEnvironment + prop*16 holds through prop
  0x54. CEnvironment::SetProp opens with cmp edi,54h followed by a JA, so the
  two ids 0x55 and 0x56 would write 32 bytes past its last record. That is why
  the state is tracked outside the array and the draw had to be added rather
  than substituted for an existing one.

- NOT YET CONFIRMED IN A BUILD OR IN PLAY. All four fixes are in source with
  tests validated against known-bad builds -- removing each fix fails its own
  test -- but they have not been through a matrix build, and nobody has seen a
  prop on a table in a running game. The ledger row and the README both say so,
  and the packaged GUI description was updated too, since that is the text a
  player actually reads before enabling the setting.

- A NOTE ON HOW THIS WAS NEARLY MISSED. The draw installer was checked earlier
  in the same session and found to be DEFINED and CALLED, the sprite PNGs were
  present in the player's install folder, and the build manifest recorded the
  hook as "installed". That is four pieces of agreeing evidence, and the
  conclusion drawn from them -- that the feature now worked and the docs saying
  otherwise were stale -- was wrong. Reachability answers whether code runs,
  never whether it produces the intended result; a feature also depends on
  resources the code path does not mention, and reserved-but-unpopulated space
  fails silently because sizes look right and offsets stay valid.

- THE FAULTING INSTRUCTION, resolved from the COFF symbol table of

      ?TakePosition@CVillagerAI@@QAEXAAVCVillager@@@Z, .text$mn + 0x3D
      0x4C8ACE   cmp dword ptr [esi], 0
  Its call targets were read from that object's relocation table, which names
  every one:
      +0x00D  theGameState::Get()
      +0x023  CVillagerPlans::ForgetPlans(villager, false)
      +0x038  CVillagerAI::DecideWhatToDo(villager)    <- the loop body
      +0x045  CVillager::Stop()
      +0x04E  ldwGameState::GetRandom(int)
  So the loop is:
      +0x028  cmp dword ptr [esi], edi   ; edi == 0, and this READ SUCCEEDS
      +0x02A  jne +0x43
      +0x030  cmp edi, 0xa               ; up to ten attempts
      +0x038  call DecideWhatToDo
      +0x03D  inc edi
      +0x03E  cmp dword ptr [esi], 0     ; FAULT
  esi is set once at +0x009 (mov esi, ecx) and never rewritten in the function,
  and the read at +0x028 must have succeeded for execution to reach +0x3E. The
  window is therefore ONE CALL WIDE, and the call is the function this patcher
  inserts bytes into.

- BOTH CALLERS OF THE OUTER LOOP ARE NAMED. CVillagerManager::TakePositions
  (0x4CBF40) is the only caller of TakePosition, and has exactly two callers of
  its own, found by an exhaustive scan of every E8 in .text:
      0x49A348  inside theGameState::Load(int)         -- the save-load path
      0x4A27A4  inside theMainScene::UpdateScene()     -- the per-frame path
  Neither function is virtual; neither address is stored as a pointer anywhere
  in the image. Both callers load the same fixed manager, mov ecx, 0x718E20.

- THE ADDED-FURNITURE CODE WAS CLEARED STRUCTURALLY, each with a check:
  * the inserted payload ships as designed at 0x4C891B -- 12 bytes pushed,
    8 popped by add esp,8 plus 4 by pop ecx, balanced; and cdecl right-to-left
    order gives the callee arg0=esi (the CVillager&, confirmed from the
    pristine prologue mov esi,[ebp+8]) and arg1=ecx (stockWeight).
  * its jne lands on 0x4C896E, the real stock epilogue, on a valid instruction
    boundary, with the pops and the security-cookie check intact.
  * all 174 branches in the patched DecideWhatToDo (575 instructions) land on
    decoded instruction boundaries and none escapes the function. There are no
    indirect jump-table dispatches in it.
  * esi discipline is structurally identical to the pristine object: one ret,
    one pop esi, and the only writes to esi are the prologue load and that pop.
  * all five added behaviour handlers are 78 bytes with 2 branches and no bad
    targets, each resolved from its single SetMacro registration.
  * behaviour ids 0xB1-0xB4 and 0xB8 are genuinely unregistered -- verified
    against the pristine Behavior.obj with the scan bounded to
    CBehavior::CBehavior via the symbol table: 387 stock registrations, max id
    0x19A, and those five among the 24 free ids below it.
  * the cloned candidate records land at villager+0xFB88..0x10208, far below
    the behaviour label buffer at 0x1BBA8 and the struct end at 0x1CC0C.
  * CVillagerManager::TakePositions is BYTE-IDENTICAL to the pristine object
    with call operands masked, so the patcher did not touch the outer loop.

- THE CONTRADICTION. esi is a villager slot, VillagerManager + 0x1CC70 +
  index * 0x1CC0C, so the thirty slots span 0x735A90..0xA943F8. That is inside
  .data (VA 0x572000..0xB7E76C) and inside SizeOfImage (image ends 0xBAD000),
  which is committed memory: a read there cannot raise an access violation.
  Yet the event log records a real 0xc0000005 reading exactly there.
  One of those premises must be wrong, and the honest position is to say so
  rather than choose a story. Candidates not yet excluded: the manager not
  being at 0x718E20 at fault time; a third entry into TakePositions; or the
  outer loop's bound being wrong in the failing run.

- RULED OUT, so nobody re-runs them:
  * stack exhaustion. DecideWhatToDo's own frame is sub esp,0xCF0, but the
    calls are sequential rather than nested, PE stack reserve is 0x100000, and
    it does not call TakePosition, TakePositions or itself.
  * the outer loop walking out of .data. It would need 38 iterations to leave
    the section and its bound is 30.
  * the one-slot stack-buffer overflow in TakePositions. edi can reach 30 and
    the buffer holds 30 entries before the cookie at ebp-4, so a 30th write
    lands on the cookie -- but that produces a fast-fail (0xC0000409) in the
    epilogue, not an access violation inside the callee. It is also stock code,
    byte-identical to the pristine object.
  * the pet equivalent. CPetAI::TakePosition carries the same loop shape in
    PetAI.obj, but the pattern occurs exactly ONCE in the shipped executable,
    at the fault address, and TakePosition has exactly one caller.

- A DEFECT FOUND ON THE WAY, recorded but deliberately NOT fixed because the
  owner has not reported it and it is outside what was asked: the behaviour
  label cache, gVF2BehaviorLabelCache, holds 64 raw CVillager* entries and is
  never cleared -- not on save load, not on new game --  and
  VF2BehaviorLabelCacheStillActive dereferences them. It is NOT an access
  violation: villagers live in a fixed array, so a stale pointer addresses
  valid mapped memory that now holds a DIFFERENT villager. That is a
  wrong-label bug, not a fault.

- METHOD NOTES, both of which produced a confidently wrong answer during this
  investigation and were caught before being acted on:
  * a section header's VirtualAddress field is an RVA. Adding the image base to
    a value that already includes it produced ".data extends past SizeOfImage",
    which looked like a spectacular finding and was arithmetic.
  * scanning a whole image for a shaped byte sequence matches unrelated code.
    Counting SetMacro registrations across the executable reported 423 ids
    including 0x3FF; bounding the scan to the constructor via the object's
    symbol table gave 387 and a clean maximum of 0x19A.

B181 startup crash: the added furniture is NOT the cause, and it is intermittent
- The entry above records the investigation as it stood when only the B181
  crash was known. Two pieces of RUNTIME evidence have since settled the
  attribution question, and both supersede everything the static analysis
  could establish.

- THE FULL CRASH HISTORY. Reading fourteen days of Windows Application Error
  events rather than only the two the owner reported gives EIGHT crashes across
  FOUR builds:
      Sep 2 17:35  B178                  fault offset 0x0c7aae
      Sep 2 17:49  Playtest 2            fault offset 0x0c7b1e
      Sep 2 18:16  Playtest 2            fault offset 0x0c7aae
      Sep 2 18:17  Playtest 2            fault offset 0x0c7aae
      Sep 2 18:23  Playtest 2            fault offset 0x0c740e
      Sep 4 23:53  B180                  fault offset 0x0c869e
      Sep 5 13:16  B181                  fault offset 0x0c8ace
      Sep 5 13:22  B181                  fault offset 0x0c8ace
  The four Playtest 2 records carry four DIFFERENT PE timestamps, so that is
  four separate rebuilds crashing, not one build four times.

- EACH RECORD WAS MATCHED TO A BINARY BY PE TIMESTAMP, which is the only
  reliable way to know which build a crash record belongs to. Three of the
  faulting binaries survive on disk: B181, B180, and the B178 at
  outputs/VF2-B178-matrix-20260902-final_all_enabled. All three disassemble at
  their own fault offsets to the SAME instruction in the SAME function:
      cmp dword ptr [esi], 0
  inside the ten-attempt retry loop of
  ?TakePosition@CVillagerAI@@QAEXAAVCVillager@@@Z, whose loop body is
  CVillagerAI::DecideWhatToDo.

- THE ADDED FURNITURE IS NOT THE CAUSE. B178 and B180 contain ZERO of the five
  added behaviour registrations -- searched for as their SetMacro entries,
  68 <id32> 8b ce e8, for ids 0x0B1, 0x0B2, 0x0B3, 0x0B4 and 0x0B8 -- and both
  crash identically. B178 did so on 2 September, three days before those
  behaviours existed at all. A feature that is absent cannot cause a crash that
  is present.
  That single comparison establishes what nine structural checks could not.
  Payload bytes, argument order, stack balance, branch target, all 174 branches,
  esi save and restore, caller-frame writes, the gate-off path, id collisions
  and record bounds all came back clean, and none of them could EXONERATE the
  added code, only fail to incriminate it. The runtime comparison does what the
  static analysis could not.

- AND IT IS INTERMITTENT. The Playtest 2 save folder holds a village file
  written 5 September 01:39:44, hours after that build's four crashes on
  2 September, and its bytes differ from the B180 folder's copy. So that build
  loaded a save, ran, and wrote it back successfully. The crash is not
  deterministic per build.
  This also disposes of an earlier inference recorded above. B181 having left
  ldwLog.txt untouched was read as a bound on how far execution got; it is not.
  Playtest 2's log was last written 31 August and that build saved on
  5 September without touching it, so the log is written only on occasional
  events -- a blocked path, a timer warning -- and never at startup or
  shutdown. The inference was void, not merely weak.

- WHAT REMAINS UNEXPLAINED. esi is a villager slot and is READABLE at the loop
  head and again at TakePosition+0x28, and unreadable at +0x3E. That is a
  one-call-wide window around DecideWhatToDo, and no static examination of
  either function accounts for it.

- RULED OUT, each with a check rather than an argument:
  * An esi overrun. The loop head reads [esi+0x1BB84], 113,540 bytes higher
    than the faulting [esi], so the high read always leaves the section first.
    There is NO index at which [esi] is unmapped while [esi+0x1BB84] is mapped,
    so an out-of-range esi always faults at the loop head, one call earlier
    than the observed fault. The villager array also has eight further slots of
    headroom inside .data past its legitimate thirty.
  * Stack exhaustion. The calls are sequential rather than nested, the PE stack
    reserve is 0x100000, and DecideWhatToDo does not recurse.
  * The one-slot stack-buffer overflow in CVillagerManager::TakePositions. It
    would overwrite the security cookie and fast-fail (0xC0000409) in the
    epilogue rather than access-violate inside the callee, and that function is
    byte-identical to the pristine object.
  * The CPetAI equivalent. CPetAI::TakePosition carries the same loop shape in
    PetAI.obj, but the pattern occurs exactly once in the shipped executable,
    at the fault address, and TakePosition has exactly one caller.
  * Comparison against vanilla. This is USELESS as a baseline and should not be
    attempted again: the recompile is different enough that the best match for
    a 40-byte window from the modded build is 13 of 40 bytes somewhere in
    vanilla, which is noise. "Absent from vanilla" is not evidence the patcher
    wrote something. What CAN be compared is bounds rather than bytes, and
    those agree: both builds bound their villager walks at 0x1e at exactly
    twenty sites, so the recompile changed codegen and not the logic.

- THE ONE INPUT THAT WOULD NARROW IT is whether any build has ever launched
  cleanly on the first attempt, or whether launching usually takes a couple of
  tries. An intermittent launch-time fault has a different search than a
  deterministic one, and the evidence above says this is the former.

The faulting loop is the GAME'S OWN CODE, present in the pristine object
- The two entries above establish that the crash predates the added furniture
  and is intermittent. This settles the remaining attribution question
  outright, and it does so without depending on any crash record.

- THE PRISTINE OBJECT CONTAINS THE FAULTING INSTRUCTION.
  work/desktop_obj_files/VillagerAI.obj is gitignored and is extracted from the
  player's own installation -- it is the game's shipped code, not anything this
  patcher generates. Disassembling
  ?TakePosition@CVillagerAI@@QAEXAAVCVillager@@@Z from it:

      +0x0028  393e           cmp  dword ptr [esi], edi
      +0x002A  7517           jne  0x43
      +0x0030  83ff0a         cmp  edi, 0xa            <- the ten-retry bound
      +0x0033  7d0e           jge  0x43
      +0x0035  53             push ebx
      +0x0036  8bce           mov  ecx, esi
      +0x0038  e800000000     call <CVillagerAI::DecideWhatToDo>
      +0x003D  47             inc  edi
      +0x003E  833e00         cmp  dword ptr [esi], 0  <- THE FAULTING READ
      +0x0041  74ed           je   0x30

  The byte pattern 47 83 3e 00 74 ed occurs once in the whole object, in that
  function. The retry loop, its bound, and the exact instruction that faults
  are all present BEFORE the patcher touches anything.

- WHY THIS IS STRONGER THAN THE CRASH-RECORD ARGUMENT. That argument rests on
  B178 and B180 crashing identically while containing none of the five added
  behaviour registrations, which is sound but depends on correctly attributing
  crash records to binaries. This does not depend on the crash at all: the
  faulting instruction exists in untouched game code, so no part of the patcher
  wrote it.

- WHAT IT DOES NOT ESTABLISH. The loop being stock does not prove the patcher
  cannot CAUSE it to fault. Whether something in the build makes esi go bad
  inside DecideWhatToDo is a separate question that an object file cannot
  answer. It removes "the patcher introduced a bad loop" from the table; it
  does not close the investigation.

- A CORRECTION TO AN EARLIER LINE OF ATTACK, recorded because it was pursued at
  length. A register-agnostic decoded scan of the vanilla executable found ZERO
  up-to-ten retry loops re-checking a dereferenced pointer, against one in every
  modded build, which looked like evidence the recompile had introduced it. It
  is not. The pristine object settles that vanilla contains the identical logic
  and merely expresses it in a form the pattern could not match -- retail
  codegen may inline, unroll, or keep the counter in memory.

- THE GENERAL RULE, which cost three separate mistakes in one investigation:
  AN ABSENCE FOUND BY PATTERN MATCHING IS NEVER EVIDENCE OF AN ABSENCE IN FACT.
  It is evidence about the pattern. The three instances were a whole-image scan
  reporting eleven behaviour registrations in the unpatched vanilla executable
  (impossible, so the method was wrong rather than the data); a check that
  symbol names were absent from a release build (they are stripped, so it
  answers nothing); and the vanilla loop scan above. A decoded scan is stronger
  than a raw byte scan and is not immune. The tell is the same every time: a
  result that would be surprising if true needs a second, different artifact
  before it is believed -- not a tighter pattern.

The crash is in theGameState's CONSTRUCTOR, and it is deterministic
- The owner answered two questions that reshaped this entirely: "B181 doesn't
  even open. it crashes" and, asked whether it had ever started, "no b181 has
  never opened successfully". So the fault is not intermittent and does not
  involve loading a family, a menu, or any player action.

- THE PATH, resolved from the object symbol tables rather than guessed:

      theGameState::theGameState()            <- THE CONSTRUCTOR
        -> theGameState::Load(int)             0x499F10
           -> CFurnitureManager::LoadState     0x467BF0  (gates the next call)
           -> CVillagerManager::TakePositions  0x4CBF40
              -> CVillagerAI::TakePosition     0x4C8A90
                 -> cmp dword ptr [esi], 0     0x4C8ACE   <<<< FAULT

  The naming misled the investigation for a long time. theGameState.obj
  defines TWO Load symbols -- ?Load@theGameState@@UAE_NH@Z and
  ?Load@theGameState@@QAEXXZ -- as well as LoadCurrentGame and Init. Only the
  first calls TakePositions, and it also calls CVillagerManager::LoadState.
  Asking what references THAT function gives exactly one caller in the entire
  object set: ??0theGameState@@IAE@XZ, the constructor. Nothing else calls it.

- WHY THIS RECONCILES EVERY FACT, including two that never fitted:
  * "doesn't even open" is accurate. The crash happens during theGameState
    CONSTRUCTION, before a window is drawn -- which looks like never starting
    from outside while being some way into initialisation.
  * it is deterministic because a constructor runs on every launch,
    unconditionally.
  * the earlier finding that TakePositions is on the save-load path was right
    about the mechanism and wrong about the timing. That path runs at STARTUP,
    not when a player picks a family.
  * theMainScene::UpdateScene, the other caller of TakePositions, never
    mattered: the game dies before a scene exists.

- THE FAULTING CODE IS IDENTICAL IN A BUILD THAT NEVER CRASHED. B174.2, built
  30 August and with no crash record, has the same TakePositions loop-head
  signature (one hit in each binary) and a byte-identical loop tail:
      B174.2  568bcee8e5caffff4381c60ccc010083fb1e7cae
      B181    568bcee8e5caffff4381c60ccc010083fb1e7cae
  Same stride 0x1CC0C, same bound 0x1E, same call. The difference between the
  two builds is not in this function.

- WHAT THIS RETIRES. Every "intermittent, frequency-shifted" framing the
  investigation had been reasoning within, and with it the Playtest 2
  succeeded-on-Sep-5 datapoint as evidence about B181: different build, and
  B181's own record is two attempts, two crashes, no successes. A deterministic
  failure in code that a near-identical build does not exhibit is a far tighter
  target than an intermittent one.

- WHAT REMAINS. Something in B181 makes that walk fault on every launch while
  B174.2 does not, and the faulting function is identical between them. The
  narrowest remaining target is theGameState's constructor itself and whatever
  it sets up before Load runs.


- WHAT CHANGED IN THE DATA THAT WALK READS. The faulting function is identical
  between a build that crashes and one that does not, so the difference is in
  what it walks. Comparing the INSTALLED trees rather than the release staging
  directories -- staging holds 84 placement maps, an installed game 327 or 328
  -- five maps differ between B179, which boots, and B180, which does not:

      InvisibleLounger.png.fmap       154 occupied cells -> 12
      InvisibleSpaLounger.png.fmap    154 -> 12
      InvisiblePatioTable.png.fmap    241 -> 8
      InvisiblePicnicTable.png.fmap   237 -> 8
      SpaLoungerStd.png.fmap          new in B180

  Every one of the other 322 maps is byte-identical, and B181 differs from B180
  in no placement map at all.

- THE CAUSE, STATED PRECISELY. The tracked desktop-safe maps are NOT damaged.
  They are generator output, documented in the B156 ledger, and 33 of the 34
  are byte-identical to what B179 ships; the one exception is Patio_table,
  differing by the two anchor cells 9c18bec corrected, at the same occupancy.
  A sparse map is correct under the donor's OWN name.

  What ee5c306 changed is which file a BORROWING item receives. A donor has two
  maps, its own sparse desktop-safe one and the raw mobile map it was cut from.
  A borrower has neither, so the map it is handed is the only thing describing
  where the piece is solid. Before that commit borrowers fell through to the
  donor's raw map; after it they took the sparse one. It is absent from B179
  and present in both B180 and B181.

  The sparse map is small because a desktop-safe copy keeps a cell's low half,
  which is right for a peep-slot anchor and empties everything else: 24,748 of
  the 42,987 occupied cells across the 327 maps installed with B179 -- 57.6% --
  carry a type with a zero low half, and the most common occupied cell in the
  stock game, 0x01080000, is one of them.

- THE FIX. A borrower keeps the donor's geometry and takes only the anchor
  cells in their translated desktop form. Verified against the B179 install:
  all four borrowers reach B179's occupancy with every non-anchor cell
  byte-identical, 254/254, 254/254, 315/315 and 344/344. The donor-named maps
  are untouched and still install at 12, 8 and 8 cells. No tracked asset
  changes, so the ten validators that reject 0x0001 never fire.

  An earlier attempt repaired the three tracked maps instead. That was wrong:
  the exporter copies pc_fmaps/<donor> to Assets/<donor>, so it would also have
  installed full maps under the donor names, which B179 does not do.

- ON 0x0001. It is ordinary desktop collision geometry, not mobile-only
  metadata: the exact value occurs 3,458 times across 102 of the 327 maps
  installed with B179, and B179's own shipped InvisiblePatioTable carries 43 of
  them and InvisiblePicnicTable 50.

- WHAT IS STILL NOT ESTABLISHED. That this explains the fault. The borrowed
  geometry is what changed across the boundary and restoring it is a fix for a
  real defect on its own terms, but the mechanism is untraced. Whether a path
  through the loop body can leave the stack displaced, so that its pop edi and
  pop esi read neighbouring slots before mov esp,ebp repairs the stack pointer,
  is unresolved: the function has a single return path, no displacement has
  been demonstrated on it, and the observed edi == arg_0 + 1 is equally
  explained by the caller's own inc edi immediately before the fault. Settling
  it needs a hardware watchpoint under a debugger, which is live execution and
  the owner's decision. Until then the accurate statement is that the emptied
  geometry was sufficient to trigger the crash, not that the crash is
  understood.
