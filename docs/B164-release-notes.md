# B164 release notes

## Context

Follow-up release after PR #9 (Bathroom 1/2 curtain hook verification and
comment fix, plus the new Bathroom 2 native-renovation purchase gate) landed
on `main`.

## `work/build_matrix.ps1` is a recreation, not a restoration

The prior `Redesigned`/`Last Matrix Build` GitHub pre-releases were built by a
script with this same name and description (one reusable engine plus two
small JSON configs, replacing the old pattern of hand-copying a whole
`build_bNNN_matrix.ps1` per release; fails closed if a variant's generator
manifest disagrees with whether a seed was actually configured for it). That
script was never committed to the repository and was not recoverable from any
local checkout on the machine it was built on -- it was written fresh against
the release notes' description, not restored byte-for-byte. Committed this
time, at `work/build_matrix.ps1`, alongside its two config files:
`data/vf2/build-matrix-toggles.json` (the stable 19-variant matrix) and
`data/vf2/build-matrix-release-b164.json` (this release's exe name/output
prefix/seed paths).

## A real compile bug found and fixed along the way

Standing up a working native build (to actually run this engine, not just
write it) surfaced a genuine compile-ordering bug in PR #9's Bathroom 2 gate
that none of the Python-level tests had caught, because
`vf2_special_upgrade_effects.cpp` is assembled from several separately-built
text blocks written by different generator functions, called in a specific
order by `main()`, and two of PR #9's new functions
(`VF2NativeBathroom2Owned`, and a `VF2ApplyPriceMultiplier` forward
declaration) were defined/declared in the wrong one of those blocks relative
to where `CInventoryManager`'s one real, method-bearing definition in the
translation unit actually ends up. A pattern-matching Python test can't catch
this class of bug; only compiling the real output can. Fixed by moving the
real bodies to where `CInventoryManager` is already complete
(`write_outfit_store_helpers`'s own output, beside `VF2ApplyPriceMultiplier`'s
real definition) and forward-declaring them where `ai_bathroom2_cpp` needs to
call them, matching the same pattern already used by other pre-existing
functions like `VF2ToggleB150PriceMode`. Added
`test_ai_bathroom2_styles_are_gated_behind_native_renovation` (now running the
real generator functions in the real call order and inspecting actual
emitted output, not just Python source text) to guard against a regression.

## Local build environment used

This machine's `work/` gitignored build cache (desktop_obj_files,
vanilla_runtime_payload, desktop_runtime_dlls, generated_import_libs) was
populated from a sibling checkout
(`Documents/Codex/Virtual-Families-2-Restoration-Addition-Patcher`) already
present on this machine, plus `work/make_import_libs_from_dlls.py` run fresh
against the runtime DLLs. The vanilla `Virtual Families 2.exe` used matches
the project's already-pinned reference fingerprint (SHA-256
`1582d9e84e1c32f51475be17335c5137c592cebf809748d401ccef99a32b73c3`, matching
`docs/offline-patcher.md`'s recorded B103 target).

## Seeds

No trustworthy same-source-commit seed directories existed locally, so this
release's per-variant seeds reuse the most recent available prior build
output (`VF2-B162.1-matrix-fix2-20260813-*`, 2026-08-13) as their
static-asset carry-forward base -- some assets (e.g. VF3 TV fmaps) are only
ever regenerated by carrying them forward from a prior build's payload, not
purely from `work/assets/`, matching how every prior release in this
project's history has always seeded. The generator always regenerates its
own patch content fresh from the current `work/patch_mobile_furniture_pack.py`
regardless of seed age; `build_matrix.ps1`'s fail-closed seed-consistency
check (configured seed vs. the generator's own record of what it did) ran
clean for every variant.
